# M7b — the first model-planner run, 2026-10-28

Status: record of one evaluation run. It holds aggregate figures, case IDs from the
committed gold file and public digests only (the M7b data rules:
[`m7b-gold-labels.md`](m7b-gold-labels.md#what-is-committed) and the
[runbook](../runbook.md#fetch-the-inputs)); the evidence sets, the model replies and the
report itself stay in the operator's local result directory. Cases, labels and the
`baseline` and `holdout` splits are defined in [`m7b-gold-labels.md`](m7b-gold-labels.md).

What the run shows: the DeepSeek adapter, the model and the structured plan protocol work
on real data, with no unavailable, timed-out or rate-limited planner call. It does not
show that the model planner improves an investigation. Where the two planners differ, the
cause is mostly retrieval, how the request is interpreted, or the stop rule, which both
share, not the plans.

not; it does not count runs that stopped too late. `affectedness_violation` is 0 in every
run, but no run output an applicability item, so the figure does not show that a version
question was answered.

The three runs whose ending differs:

- `kamailio-version-affected` run 3 and `suci-deconcealment` run 3 stopped with
  `budget_exhausted` (wall time) and no answer; their other four runs match or come close
  to the deterministic coverage (SUCI 1.0 in each; Kamailio 0.90 to 1.0, a mean of 0.96
  against 0.95). Both are the collection stall below, not a plan.
- `diameter-core` (holdout) run 5 stopped with `budget_exhausted` (context bytes). In 3
  of its 5 runs the model's plan raised implementation coverage from 4/13 to 6/13, each
  time through the same round-1 search, worded differently from the policy's. In run 5 a
  second search went over the context budget and was discarded, which ended the run.

The lower `wrong_stop` rates of the model part come from two of those budget stops
(`kamailio-version-affected` run 3, `diameter-core` run 5), not from better stopping; the
SUCI budget stop instead lost a sufficient answer.

## Causes

**1. Collection stalls in lexical search.** The two failed runs stalled
in one `cve_search` step against a 30 s budget.
The deterministic run searched the same SUCI terms. The 30 s deadline
did not bound these steps: the call runner gives control back at the deadline only when
its waiting thread can run, and a full collection holds the interpreter lock, so the runs
ended late.

An offline probe reproduced it without the model. It built the BM25 index over the
store, then ran eight searches four times each. Two of the 32 searches stalled,
each during a single generation-2 collection; every other
search had none.

After loading the store and building the index, the process holds
objects the collector tracks, most of them the served records; the index adds objects
per record (a term counter, a field map and its term sets). A search scans every record
and builds a validated match for each record that holds any query term, then keeps 20.
Query terms that occur in many records make that hundreds of thousands of matches: `de`
(from "de-concealment") is in 303,750 of the 396,211 records, `2` in 114,519, `affected`
in 46,472. Those allocations trigger the full collection, which scans every tracked
object. The same terms explain why searches with them remain costly even without a
stall, while a search whose three terms each occur in at most 22 records is faster.



**2. Generic terms admit unrelated records.** `srsran` occurs in no record, so all 20
results of `srsRAN vulnerabilities` match only `vulnerabilities`; the answer is non-empty
and the run stops as `sufficient`. Both planners do this every time. Lexical search
admits a record that matches any term, and with no topic card nothing filters candidates
by subject afterwards.

**3. Version questions are not recognised.** `kamailio-version-affected` and
`open5gs-named-affected` name a product and version only in the question text, and their
filters are empty. Affectedness becomes an answer source only through product filters, so
no run asks for it, reports `applicability_unknown` or leaves a gap; every run that
returns CVEs stops as `sufficient`.

**4. Protocol context has two gaps.** FiGHT is searched only through a topic card, and
the only card is 5G-AKA. `gtp-mobile-core` and `diameter-core` therefore have no protocol
action, and protocol-only questions without a card end before planning. Under the 5G-AKA
card, the FiGHT search ranks techniques by the number of terms matched, then by technique
ID, and keeps 20 of the 30 that match. Among the techniques matching one term, the cut
falls by ID: FGT5044, matched only through `SUPI`, is 30th. FGT1036.501 is not matched at
all: its text speaks of authentication vectors, and the terms the card sends to FiGHT (its
name, aliases and entity names) do not.

**5. An answer is taken as sufficient.** The assessment returns `sufficient` once the
answer holds any CVE or technique, provided no evidence was invalid, no cap was breached,
no admitted step saw an answer source fail, and no product filter made affectedness an
answer source. A source never consulted does not count as failed. A `mixed` question with CVEs and no
protocol context stops; so does a product question answered by generic matches.

**6. Round 2 asks for a plan when none is possible.** `rejected-cve-id` looked up its
only named ID in round 1 and has no other term or topic. Round 2 is entered because a
configured model is consulted even when the policy has no refinement. The model's empty
step list says there is nothing left to do, but the plan schema requires at least one
step, so the reply is recorded as `malformed_plan`.

## Limits

Seventeen cases, chosen and labelled before the run, with no claim of representativeness.
This record reads the holdout figures once, before any change. The checks above show the records and
figures are consistent; they do not re-judge the labels or replay the corpus.

## What follows

The work order, agreed with the owner: the evaluation corrections in this record; lexical
search first made fast with byte-equal results, then given an admission rule against
generic-only matches, measured as the precision it gains and the required or allowed
items it loses; per-request evidence needs, met only by relevant evidence and never read
from gold; FiGHT search from the question's own terms without a card (a change to M3's
topic gate, with card exclusions still applied). Development uses the baseline cases and
synthetic cases. The holdout is read again only after these changes, to check them
([`m7b-gold-labels.md`](m7b-gold-labels.md#holdout)), and the next model run
follows only when the deterministic path is stable.
